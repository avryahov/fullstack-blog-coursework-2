# Migration Plan

## Цель

Перенести reference-проект блога из frontend-only архитектуры с `json-server` и локальным BFF в full-stack приложение с отдельными Frontend, Backend и DevOps-слоями.

## Основные зависимости

1. Сначала фиксируется архитектура и структура репозитория.
2. Затем проектируются MongoDB-сущности и API contract.
3. После этого реализуется backend.
4. Только затем frontend переводится на новый API.
5. Docker Compose и deploy допускаются только после локальной full-stack проверки.

## Этапы реализации

### Этап 1. Bootstrap нового репозитория

Результат:
- созданы `Frontend/`, `Backend/`, `DevOps/`, `docs/`;
- создан базовый `README.md`;
- зафиксированы архитектурные документы;
- настроен git workflow для атомарных коммитов.

### Этап 2. Backend design baseline

Результат:
- определены сущности MongoDB;
- зафиксированы индексы и связи;
- определен API contract;
- выбрана схема авторизации.

### Этап 3. Backend skeleton

Результат:
- создан Express application skeleton;
- подключена MongoDB;
- добавлены базовые middleware, routes, controllers;
- подготовлена env-конфигурация.

### Этап 4. Seed migration

Результат:
- данные из старого `db.json` перенесены в seed-формат;
- роли, пользователи, посты и комментарии заполняют MongoDB;
- пароли хешируются при seed.

### Этап 5. Auth and access

Результат:
- реализованы register/login/me;
- роли валидируются на backend;
- frontend перестает хранить пароль в `sessionStorage`.

### Этап 6. Posts and comments API

Результат:
- реализованы list/detail/create/update/delete для постов;
- реализованы create/delete для комментариев;
- поиск и пагинация перенесены на backend.

### Этап 7. Admin API

Результат:
- реализованы users list/delete;
- реализованы roles list и user role update;
- access checks выполняются только через backend middleware.

### Этап 8. Frontend migration

Результат:
- удален frontend BFF;
- добавлен единый API client;
- страницы переведены на новый backend;
- UI и пользовательские сценарии сохранены.

### Этап 9. Local acceptance

Результат:
- frontend, backend и MongoDB запускаются локально;
- сценарии login/register/posts/comments/users проходят вручную;
- ошибки и пустые состояния обработаны.

### Этап 10. Docker Compose

Результат:
- stack поднимается одной командой;
- backend, frontend и MongoDB объединены в общий локальный контур;
- подготовлена база для reverse proxy.

## Риски миграции

### Риск 1. Перенос клиентской логики без разграничения ответственности

Последствие:
- backend получится формальным;
- критичные проверки останутся на frontend.

Контрмера:
- переносить только UI и UX-логику;
- весь доступ и операции данных выносить в backend.

### Риск 2. Ломка UI из-за ранней замены всего слоя данных

Последствие:
- тяжело локализовать регрессии;
- миграция затянется.

Контрмера:
- сначала стабилизировать контракты;
- переводить страницы по сценариям, а не все сразу.

### Риск 3. Несогласованные data contracts

Последствие:
- появится лишний mapping и дублирование;
- возрастет шанс ошибок в ролях и датах.

Контрмера:
- зафиксировать единый `camelCase` contract на стороне API;
- ограничить преобразования model layer внутри backend.

### Риск 4. Слабая схема auth

Последствие:
- небезопасное хранение учетных данных;
- ложная имитация защищенности.

Контрмера:
- убрать пароль из клиента;
- внедрить backend token auth;
- access checks делать middleware-слоем.

### Риск 5. Преждевременный DevOps

Последствие:
- будет контейнеризован нестабильный стек;
- отладка усложнится.

Контрмера:
- сначала локальная full-stack приемка без deploy;
- затем docker-compose;
- затем reverse proxy и VPS этап.

## Правило коммитов

Коммиты должны быть:
- атомарными;
- тематическими;
- проверяемыми;
- без захвата локальных служебных файлов.

Рекомендуемый порядок коммитов:
1. bootstrap structure
2. backend skeleton
3. mongodb models and seed
4. auth api
5. posts api
6. comments api
7. admin api
8. frontend api migration
9. compose and local runtime

## Что нельзя делать

- делать массовый перенос кода до фиксации API и моделей;
- использовать `git add .`;
- смешивать backend-проверки с frontend-only access logic;
- переходить к deploy до локальной full-stack приемки.
